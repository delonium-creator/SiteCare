## Известные ограничения облачной Cowork-сессии (не баги проекта!)

Эти вещи не работают из облачной сессии Claude (Home/Cowork) и это не связано с кодом проекта:

1. **`npm install` не может поставить `miniflare`/`wrangler`** — сетевая политика песочницы
   блокирует часть пакетов npm-реестра (`403 host_not_allowed`). Из-за этого 3 тестовых файла
   (`gateway.test.js`, `integration.test.js`, `platform.test.js`) не запускаются в облаке —
   на обычном компьютере или в GitHub Actions они отрабатывают нормально.
1a. **На локальной Windows-машине те же 3 файла падают иначе** — `npm install` проходит, но
    сами тесты валятся с `Error: write EOF` (обрыв IPC-канала до подпроцесса `workerd`,
    который поднимает Miniflare для эмуляции D1). Проверено 2026-08-16: ошибка стабильно
    воспроизводится на каждом прогоне, всегда в одних и тех же тестах, без единого
    assertion-провала — то есть это несовместимость Miniflare/workerd с этой конкретной
    Windows-средой, а не баг кода. Надёжный сигнал по этим файлам — только GitHub Actions
    (`ubuntu-latest`), локально на Windows им доверять не стоит. `node --test --test-force-exit`
    даёт увидеть детали ошибки вместо зависания, но саму проблему не решает.
2. **`git push` из облачной сессии не работает вообще**, даже с personal access token —
   известный открытый баг Anthropic: proxy блокирует пуш в репозитории, не входящие
   в "authorized repository set" сессии, обхода пока нет.
   Issue: https://github.com/anthropics/claude-code/issues/76248
   Из-за этого изменения из облачной сессии в GitHub переносятся вручную (см. ниже).
3. Один тест (`assets.test.js` — "Windows launcher stays ASCII with CRLF") падает в Linux-среде,
   потому что `START-SITECARE.bat` сохранён в git с LF, а тест ожидает CRLF. На Windows это
   не всплывает благодаря `core.autocrlf`. Не исправлено — можно добавить `.gitattributes`
   (`*.bat text eol=crlf`), если понадобится тест зелёным везде.

## Как переносить изменения из облачной сессии в GitHub (пока баг с пушем не пофиксили)

- Маленькая правка (1-2 файла) — скопировать готовое содержимое файла и вставить через
  веб-редактор GitHub (Edit → Commit).
- Много файлов — Claude собирает их в zip, присылает файлом; на github.com:
  Add file → Upload files → перетащить содержимое zip → Commit.
- После переноса в облачной сессии сделать `git pull`, чтобы синхронизироваться.

## Три реальных бага после живого теста виджета (2026-08-16)

Пользователь протестировал задеплоенный виджет на реальном сайте и прислал скриншоты трёх
настоящих проблем (не косметика — это упустил при верификации, хотя должен был поймать):

**1. Диалог «залипал» на предыдущей теме.** После вопроса про телефон без ответа
(незавершённый `dialog`) следующее сообщение — даже «Проверь состояние сайта» — снова
получало «Какой телефон вы хотите изменить?». Причина: `continueDialog()`
(`platform-assistant.js`) при НЕудачном разборе ответа просто переспрашивал тот же
вопрос вместо проверки, относится ли новое сообщение к теме вообще. Это ровно та же
проблема, что упоминалась в самой первой истории проекта (см. «Этап 2» в разделе про
восстановленную историю продукта) — просто её так и не победили. Исправлено: все
тупиковые ветки `continueDialog` (phone: stage target/location/value; button: stage
attribute/value) при нераспознанном ответе теперь возвращают `null` — это сигнал
«не продолжение диалога», и `prepareSiteChange()` обрабатывает сообщение как новое,
свежее обращение вместо зацикливания.

**2. «Выбрать на сайте» реально не работал.** Клик по номеру на опубликованной странице
просто закрывал вкладку и ничего не происходило. Вероятная причина — `window.opener`
ненадёжен для КРОССдоменных всплывающих окон: у многих сайтов (в т.ч., похоже, у Tilda)
настроена `Cross-Origin-Opener-Policy`, которая молча обнуляет `window.opener` для
попапов на чужой домен — `postMessage` в таком случае просто ничего не делает, ошибки
нет. Исправлено добавлением надёжного запасного канала связи, НЕ зависящего от
`window.opener`:
- новая таблица `platform_pending_selections` (миграция `0017_pending_selection.sql`) —
  однострочное хранилище на сайт, с TTL 10 минут;
- новый публичный эндпоинт `POST /v1/public/sites/:id/select?key=...` — загрузчик
  репортит клик туда напрямую (та же схема авторизации `key`+`Origin`, что у `/applied`);
  `postMessage` остался как best-effort резерв, но не единственный путь;
  новый авторизованный эндпоинт `GET /v1/platform/sites/:id/selection` — панель
  проверяет его при возврате фокуса на вкладку (`window.addEventListener('focus',...)`),
  что не зависит от `window.opener` вообще — просто "мы снова активны, есть что забрать?".
- Проверено: реальный fetch с тестовой страницы на `/select` (лог сервера подтвердил
  сохранение), реальный GET `/selection` вернул тот же payload. Живую двухоконную
  склейку (`window.open` → реальный фокус) в этой тестовой среде эмулировать не удалось
  (тот же нюанс автоматизации, что и раньше — попап не отслеживается как отдельная
  вкладка), но обе половины цепочки проверены раздельно и по-настоящему.

**3. Баннер режима выделения перекрывал шапку сайта.** Был `position:fixed;top:0`
на всю ширину — переделан в компактную плашку снизу по центру
(`position:fixed;left:50%;bottom:20px;transform:translateX(-50%)`), чтобы не закрывать
навигацию сайта независимо от того, как он свёрстан.

Заодно по тому же сообщению — сжатый композер и подсказки в виджете (`chat-suggestions`
теперь горизонтальный скролл в одну строку вместо стека на весь экран, `chat-send`
без текстовой подписи, только иконка), более плавная анимация раскрытия
(`cubic-bezier(.34,1.4,.64,1)`, старт с `scale(.3)` вместо `scale(.85)` — заметнее
эффект «разворачивания»), кнопка расширения виджета на весь экран (`.chat-widget.expanded`).

Пользователь справедливо отметил, что часть этого стоило поймать до показа, а не после
его сообщения — особенно баннер поверх шапки и «залипание» диалога, оба видны при
минимальном тестировании реального сценария использования, а не только структуры HTML.

## Исправление вёрстки плавающего чата (2026-08-16, после первого деплоя виджета)

Сразу после деплоя плавающего чата пользователь прислал скриншоты: текст в шапке виджета
переносился по одному слову на строку, читать невозможно. Причина найдена измерением
реальных ширин через JS в браузере (не на глаз): `.chat-panel-head` — `display:flex`
контейнер с `.chat-identity` (`display:grid`, без явного `flex-grow`) и `.chat-presence`
(бейдж-пилюля, `flex:0 0 auto`, не сжимается). Вся эта раскладка была рассчитана на широкую
панель (800+px в исходном полноэкранном режиме) — в узком виджете (400px) `.chat-identity`
сжимался под нерастягивающийся бейдж, а его `grid-template-columns:76px minmax(0,1fr)`
схлопывал текстовую колонку до ~120px. Заголовок раздувался до 413px высотой, ломая всё
остальное (зона сообщений сжималась до неприличного минимума).

Исправлено — не попыткой донастроить старую раскладку, а отдельным компактным заголовком
специально для виджета (`.chat-widget-head`, простой flex-ряд: аватар 36px + имя + статус
+ крестик), а исходный `.chat-panel-head` внутри виджета скрыт через `.chat-widget
.chat-panel-head{display:none}` (сам HTML не трогали, чтобы не дублировать logic сборки
`assistant` markup). Высота заголовка — 67px вместо 413px.

Заодно по тому же сообщению:
- Анимация раскрытия/закрытия: иконка-пузырь схлопывается в точку (`scale(0)`) при открытии
  чата и возвращается при закрытии — не настоящий shared-element morph, а два синхронно
  анимированных элемента с общей точкой отсчёта (`transform-origin:bottom right`), но
  воспринимается как единое целое.
- Автопрокрутка чата вниз при каждом открытии/обновлении (`box.scrollTop=box.scrollHeight`
  после `innerHTML` в `renderChatWidget()`) — раньше открывался с прокруткой наверх.
- Убрана дублирующая кнопка «Спросить помощника о причинах» на странице диагностики
  (была нерабочей, если виджет закрыт — `$('changePromptV45')` не существовал).
- Плашки индекса/замечаний получили подписи текстом («Индекс здоровья: 92»,
  «5 замечаний») вместо голых чисел без контекста.
- Галочки статусов (сайт/заявки/Telegram) увеличены до 30px в кружке.

Не сделано (сознательно, обсуждалось отдельно): полноценный визуальный редизайн «под
современность» — точечные фиксы выше нацелены на конкретные жалобы, не тотальная смена
стиля; перепроверка качества реальных ответов OpenAI (ключ настроен, но живой диалог не
тестировался программно, только вручную described-by-user).

## Плавающий чат + «Диагностика» вместо «Главной» (2026-08-16)

По просьбе пользователя чат-помощник вынесен из основного экрана в отдельный плавающий
виджет (иконка-робот, фиксирована справа внизу) — доступен с любого клиентского экрана
(Диагностика/Заявки/Отзывы/Настройки), не показывается оператору вне режима предпросмотра
клиента. Состояние открыт/закрыт (`chatWidgetOpen`) сохраняется при переключении вкладок
(`render()` вызывает `renderChatWidget()` в конце, независимо от `currentView`). Закрывается
крестиком или Escape.

`renderClientEdit` (вкладка «Главная») переименована в «Диагностика», рендерит только
блок состояния сайта и историю изменений — на всю ширину (класс `.diagnostics-only`,
max-width:980px), без урезанной колонки под чат. Карточки статуса (сайт/заявки/Telegram)
переведены на адаптивную сетку `repeat(auto-fit,minmax(230px,1fr))` — на всю ширину
выстраиваются в 3 колонки вместо вертикального стека.

Механика клика по логотипу помощника внутри диагностики теперь просто напоминает,
что открывается плавающий чат («Спросить помощника о причинах» → «Откроется чат в
плавающем окне справа»), сам чат больше не встроен в этот экран.

Обработчики `data-editor-action`/`data-prompt-example` переведены с `$('view')` на
`document` (делегирование), поскольку виджет чата находится вне `#view`.

Один тест (`platform-ui.test.js`) проверял старые литеральные строки интерфейса
(подзаголовок «Главной», `class="editor-layout"`) — обновлён под новую структуру.

Не сделано: перенос выбора кнопок кликом по сайту (только телефон, см. предыдущий
пункт); горячие клавиши для самой диагностики (сделан только Escape для закрытия чата).

## Точечный выбор номера телефона + «Выбрать на сайте» (2026-08-16)

Пользователь много раз жаловался, что замена телефона работает непредсказуемо: когда на
странице несколько номеров (особенно одинаковых, например плейсхолдер `111111111111111` в
двух разных местах), система не даёт выбрать конкретное место — предыдущая сессия пыталась
это решить (есть мёртвый код `choosePhoneLocation()` в `platform-assistant.js`), но не довела
до конца.

Найдена настоящая причина — в `applyPreparedChange()` (`gateway/src/platform.js`) при
применении смены телефона `scope` был **жёстко зашит как `"site"`** (значит «везде»),
несмотря на то, что вся остальная инфраструктура (запись `platform_phone_target_rules`,
применение в загрузчике через `blockId`/`occurrenceIndex`) уже полностью поддерживала
точечный `scope:'element'`. Клиент (`platform-ui.js`) при этом уже правильно отправлял
`scope` в запросе — сервер его просто игнорировал. Та же жёсткая подстановка была и в
`continueDialog()` при продолжении диалога после выбора места.

Исправлено:
- `platform.js` — `scope` теперь читается из `body.scope` (валидируется по тому же
  паттерну, что уже использовался для кнопок), по умолчанию `"site"` для обратной совместимости.
- `platform-assistant.js` — `continueDialog` сохраняет `dialog.scope`, если исходный
  кандидат по-прежнему находится в свежем сканировании; иначе безопасно откатывается на `"site"`.

Добавлена новая функция — **клик прямо по сайту** вместо угадывания по тексту:
- Новый эндпоинт `POST /v1/platform/sites/:id/assistant/locate-phone` — принимает
  `{pagePath, blockId, source, occurrenceIndex, originalDigits}` от клика, сам сканирует
  сайт свежим `scanSiteInventory()` и находит точное совпадение (не полагается на
  клиентский `candidateId`, чтобы не зависеть от рассинхронизации хэшей между сканами).
- `gateway/src/platform-core.js` (`sitecareLoaderRuntime`) — режим выделения по параметру
  `?sitecare_select=phone` в URL: подсвечивает все `tel:`-ссылки и текстовые совпадения на

## Чат-виджет: доведение до рабочего состояния (2026-08-16, третий раунд правок)

После переноса чата в плавающий виджет и рескейла интерфейса пользователь сообщил три новых
симптома: при каждом новом сообщении «чат скроллится сверху вниз», быстрые кнопки вставляли
текст в чат вместо мгновенного срабатывания, «все кнопки не работают». Разобрано и исправлено:

- **Корневая причина «одинакового общего ответа дважды подряд»** (жалоба из предыдущего
  раунда — на «Проверь состояние сайта» ассистент дважды отвечал «Уточните, пожалуйста, что
  нужно изменить»): в `platform-assistant.js` цепочка `prepareSiteChange()` уходит
  OpenAI → Cloudflare Workers AI (`askAi`/`normalizeAiProposal`) → generic fallback. По факту
  в проде срабатывает besplatная Cloudflare-модель (`@cf/zai-org/glm-4.7-flash` и т.п.), которая
  не распознаёт даже простые статусные вопросы и падает в fallback-текст
  `normalizeAiProposal()`. Сам вызов OpenAI, похоже, не отрабатывает или не настроен для этого
  класса вопросов — не чинили сам классификатор (это отдельная, более крупная задача), вместо
  этого закрыли конкретный класс жалоб точечно (см. ниже).
- **`continueDialog()` в `platform-assistant.js`** на нераспознанном ответе повторно задавал
  тот же уточняющий вопрос («Какой телефон вы хотите изменить?» и т.п.) вместо того, чтобы
  пропустить реплику дальше на свежую обработку — из-за этого диалог мог «залипать» на старом
  вопросе, если клиент фактически спросил что-то другое. Все тупиковые ветки (телефон:
  target/location/value, кнопка: attribute/value) теперь возвращают `null` при непонятном
  ответе и падают в обычный pipeline вместо переспроса.
- **Быстрые кнопки предложений (`assistantSuggestions()` в `platform-ui.js`)** переведены с
  `data-prompt-example` (подставить текст в поле и отправить через AI) на
  `data-editor-action="quick-*"` с детерминированной обработкой в новых `handleQuickAction()`/
  `injectQuickAnswer()`: «Проверь состояние сайта» дергает `/check` и строит ответ из
  `pageOk`/webhook-статуса/Telegram напрямую; «Проведи SEO-диагностику» и «Что можно улучшить?»
  берут `diagnostics.issues` из `/inventory`; «Почему могут не приходить заявки?» — чистая
  локальная логика по `form_required`/`webhook_verified_at`/`form_verified_at`. Все четыре не
  трогают AI-пайплайн вовсе, поэтому не зависят от качества классификации бесплатной модели.
  Кнопки, предложенные самим ассистентом в ходе диалога (не из дефолтного набора), по-прежнему
  идут через `data-prompt-example` — переделаны только 4 стартовые.
- **Найден и исправлен реальный баг** в первой версии `handleQuickAction`: обработчик
  `quick-check` вызывал `await load(accountId)` — полный перезапрос дашборда, который создаёт
  новые объекты сайтов из JSON и стирает клиентские поля `_conversation`/`_overrides`
  (привязанные к старой ссылке на объект). Из-за этого виджет вместо вставленного ответа
  показывал заглушку «Открываю помощника…». Исправлено: `load()` убран, вместо него
  `s.page_ok`/`s.tls_ok`/`s.loader_ok` обновляются напрямую из camelCase-полей ответа `/check`
  без потери ссылки на объект. Обнаружено и проверено вживую через локальный мок-сервер (не
  только чтением кода) — сетевой запрос уходил верно, но UI не обновлялся, пока не убрали
  `load()`.
- **Высота и скролл**: `.chat-widget` был с фиксированной `height:min(600px,...)`, из-за чего
  контейнер `.assistant-chat` со скроллом всегда занимал одну и ту же высоту, даже когда
  сообщений мало — визуально выглядело как «скролл на пустом чате». Заменено на
  `height:auto;max-height:min(600px,calc(100vh - 60px))`, `.assistant-chat` — на
  `flex:1;min-height:0;overflow-y:auto`: виджет растёт вместе с сообщениями и включает скролл,
  только когда контент реально превышает потолок. Проверено вживую: с одним приветствием —
  505px без скролла; после одного ответа — 476px, всё ещё без скролла; после 4 обменов
  репликами — упирается в потолок 600px и появляется скролл, как и задумано.
- **Скролл к последнему сообщению** переведён с прямого `box.scrollTop=box.scrollHeight` (не
  успевал сработать до перерисовки DOM) на двойной `requestAnimationFrame(...)`, чтобы браузер
  успел применить layout перед скроллом.

Проверено вживую на локальном моке (`node:http` сервер, отдающий реальный `platformHtml()`):

Сознательно не сделано: сам классификатор AI для произвольных текстовых вопросов (не входящих

путаться — не переделывали, это отдельная, более крупная задача (либо чинить вызов OpenAI,

## Настоящая причина «чат постоянно скроллится сверху вниз» и диагностика по кнопке (2026-08-16)

После деплоя предыдущего раунда пользователь сообщил, что чат по-прежнему «постоянно
скроллится сверху вниз», и попросил убрать «Индекс здоровья» с страницы «Диагностика»,
заменив автоматический список проблем на кнопку, запускающую полную проверку.

- **Настоящая причина скролла**: класс `.assistant-chat` (используется и в чате-виджете, и
  в старом полноэкранном чате) имеет `scroll-behavior:smooth`. Каждый ре-рендер виджета
  (`$('chatWidget').innerHTML=...`) создаёт новый DOM-узел `.assistant-chat` со `scrollTop=0`,
  и любая последующая программная установка `scrollTop` (в т.ч. предыдущий фикс с двойным
  `requestAnimationFrame`) анимируется браузером из-за `smooth` — визуально это и есть «скролл
  сверху вниз». А происходит это не только при новом сообщении: `render()` (который всегда
  вызывает `renderChatWidget()`) дёргается фоновыми `setInterval`-опросами каждые 9–12 секунд
  (ожидание применения правки, обновление диалога с поддержкой) — то есть скролл-анимация
  срабатывала регулярно сама по себе, без действий пользователя. Исправлено: у
  `.chat-widget .assistant-chat` явно выставлен `scroll-behavior:auto`, плюс сам
  `renderChatWidget()` теперь запоминает, было ли положение прокрутки внизу и вырос ли список
  сообщений (`chatLastMessageCount`) — прокрутка к последнему сообщению происходит только при
  реальном новом сообщении или если пользователь и так был внизу; в остальных случаях позиция
  прокрутки восстанавливается как была, а не сбрасывается наверх.
- **«Индекс здоровья» убран** со страницы «Диагностика» (сам показатель `health_score` в БД
  и API не тронут — используется в дайджестах, просто не выводится этим бейджем).
- **Список проблем сайта переведён на ручной запуск.** Раньше «критические» проверки
  (TLS/доступность/код SiteCare/приём заявок) считались и показывались всегда, а более
  подробный SEO/доступность-скан подтягивался только если где-то уже был вызван `/inventory`
  (например, через кнопку в чате). Теперь на странице по умолчанию — карточка-приглашение с
  иконкой и кнопкой «Запустить диагностику»; сами три быстрых индикатора (сайт/заявки/Telegram)
  остаются видны всегда как и раньше. По нажатию кнопка показывает анимированное состояние
  «Анализирую сайт…» (вращающаяся SVG-иконка), параллельно вызывает `/check` и `/inventory`,
  затем показывает полный список замечаний (критические + SEO/доступность из
  `diagnostics.issues`) с плавным поочерёдным появлением карточек (`nth-child`-задержки в
  CSS-анимации). После первого запуска кнопка превращается в «Обновить диагностику». Как и в
  прошлом фиксе quick-check, обновление `page_ok`/`tls_ok`/`loader_ok` идёт прямым мутированием
  полей объекта сайта — без `load()`, чтобы не терять состояние переписки в чат-виджете.
- **Добавлено логирование ошибок OpenAI**: `catch` вокруг вызова `requestOpenAiAssistant()` в
  `prepareSiteChange()` (`platform-assistant.js`) раньше полностью проглатывал ошибку без
  единого следа. Добавлен `console.error('openai_assistant_failed', ...)` с сообщением,
  HTTP-статусом и `request-id` — это не меняет поведение, но впервые даёт возможность увидеть
  в `wrangler tail`, почему запрос к OpenAI не сработал.

**Про жалобу «AI вообще ничего не понимает» — расследование, не доведено до конца.**
Прямой запрос к боевой базе (`platform_conversation_messages` в `sitecare-telegram-gateway-db`)
показал: почти все ответы ассистента за 16.08.2026 (18:32–19:31) имеют
`type:"clarification", kind:"unknown"` — то есть попадают в обобщённый fallback-путь, а не
в реальную классификацию. Дневная квота AI-запросов (`platform_usage_daily`) при этом не
исчерпана (5 из 20 на starter-плане) — значит, дело не в лимите. `env.OPENAI_API_KEY` и
`env.OPENAI_MODEL=gpt-5-mini` привязаны к воркеру (видно в выводе `wrangler deploy`), то есть
код должен пытаться сначала звать OpenAI. Рабочая гипотеза: вызов `requestOpenAiAssistant()`
либо падает с ошибкой (сеть/авторизация/формат), либо превышает таймаут, и код молча
проваливается в бесплатный Cloudflare Workers AI (`@cf/zai-org/glm-4.7-flash` и т.п.), который
на свободных вопросах часто возвращает `kind` не из ожидаемого набора или вообще не
`"advice"`, из-за чего пользователь получает шаблонное «Уточните, пожалуйста, что нужно
изменить» почти на любой вопрос, не являющийся точной командой на замену телефона/графика/
кнопки. Логирование (см. выше) добавлено именно для проверки этой гипотезы, но подтвердить
её `wrangler tail`-логами в этой сессии не удалось: у сессии нет пароля/сессии от боевого
кабинета клиента, чтобы самостоятельно отправить тестовое сообщение в чат (и не должно быть —
ввод паролей за пользователя запрещён политикой безопасности сессии). Нужен один реальный
запрос от пользователя в живом чате при включённом `wrangler tail`, чтобы увидеть точную
причину и решить: чинить вызов OpenAI (не исключено, что дело в имени модели `gpt-5-mini` —
это не проверялось напрямую) или значительно переписывать сам промпт/классификатор.

## Диагноз OpenAI подтверждён и закрыт: баланс, не код (2026-08-17)

Пользователь прислал реальный вопрос через живой чат при включённом `wrangler tail` — лог
показал точную причину: `openai_assistant_failed OPENAI_RATE_LIMIT 429`. У OpenAI под кодом 429
скрываются и настоящий rate-limit, и «закончилась квота/не привязана оплата» — по характеру
(одинаковый провал на каждом запросе за день, а не изредка) это однозначно нехватка баланса,
а не частота запросов. Модель `gpt-5-mini` тут ни при чём — она валидна и по сей день значится
в официальном прайсе OpenAI ($0.25/1M вход, $2.00/1M выход).

Обсудили с пользователем реальную стоимость (по факту — копейки при текущей нагрузке, $1-2/мес
по прикидке) и способы пополнения из РФ (карта не проходит напрямую; разбирали внешний
реселлер API-ключей и «прямое пополнение чужой картой» — оба варианта отклонены как рискованные:
доступ к чужому аккаунту = риск потери уже рабочего продакшен-ключа, чужая ворованная карта =
шанс чарджбэка и списания долга на пользователя задним числом уже после траты баланса;
легитимный путь — зарубежная виртуальная карта вроде pipl.io). Пользователь решил: **пока не
пополнять OpenAI вообще** — соотношение "разбираться с картой ради AI, который сейчас не
критичен для задачи" не оправдано. Явное указание: доработать бесплatную связку (Cloudflare
Workers AI + локальный классификатор) вместо оплаты OpenAI. К вопросу об OpenAI возвращаться
только если пользователь попросит явно.

## Доработка бесплатного чат-помощника «под ключ» (2026-08-17)

По итогам решения остаться на бесплатной модели пользователь прямо потребовал: прогнать
помощника по всем возможным сценариям, потому что ошибок может быть много; все ключевые
запросы должны отрабатывать; должен быть перевод на человека; плюс отдельно перечислил баги
самого виджета (дёрганая анимация открытия, скролл, надпись в шапке, горячие команды,
неполный список проверок сайта).

**Корневая архитектурная проблема, из-за которой лечение промпта не помогло бы:** в
`prepareSiteChange()` (`platform-assistant.js`) порядок был dialog → explicit-edit → OpenAI →
Cloudflare AI → локальный `localConversation()` → generic fallback. Раз Cloudflare AI почти
всегда возвращает *успешный*, но бессмысленный ответ (не `null`), локальный слой с готовыми
ответами физически никогда не достигался — даже отличный локальный классификатор ничего бы
не изменил на старом месте в цепочке. Исправлено: добавлен новый слой
`localAssistantAnswer(prompt, siteContext)`, который теперь стоит **до** любого обращения к AI
(и OpenAI, и Cloudflare) — детерминированные, проверенные ответы на известные категории вопросов
больше не зависят от качества бесплатной модели вообще.

Новый локальный классификатор покрывает (все регулярки собраны в широкие списки фраз, не одна
жёсткая формулировка):
- **Возможности** («что ты умеешь», «чем можешь помочь», «кто ты», «расскажи о себе» и т.д.) —
  фиксированный точный ответ о реальных функциях.
- **Статус сайта** («как дела», «сайт работает?», «статус сайта») — тот же расчёт, что и у
  кнопки «Проверь состояние сайта», но по свободной формулировке.
- **SEO/технические замечания** («какие проблемы», «что не так», «seo диагностика») — строится
  из `siteContext.diagnostics.issues`, с фильтром по категории, если явно упомянуто «seo».
- **Заявки/лиды** («заявки не приходят», «лиды») — тот же расчёт, что у кнопки
  «Почему могут не приходить заявки?».
- **Перевод на человека** («позови оператора», «нужен специалист», «переведи на поддержку»,
  «живой человек» и т.д.) — включает существующий UI-механизм `supportSuggested` (полоска
  «Позвать специалиста?» с кнопкой «Связаться с поддержкой»), которым раньше управляла только
  AI/чужой JSON-ответ, теперь доступен и локально, без зависимости от AI.

**Найден и исправлен системный баг в существующих regex**: `\b` (граница слова) в JS
**не распознаёт кириллицу как символ слова** даже с флагом `u` — подтверждено напрямую в Node
(`/ты\b/u.test('кто ты')` → `false`). Из-за этого несколько паттернов, включая уже существовавшую
(добавленную раньше) проверку приветствия `/^(?:привет|...)\b/iu`, никогда не срабатывали на
короткие сообщения без хвоста («привет» без продолжения не ловилось вообще). Все `\b` рядом
с кириллицей убраны/заменены на `(?:\s|[,.!?]|$)`; `\b` оставлен только там, где слово
латиницей (`seo`, `human`) — там он работает корректно из-за пробелов по краям. Проверено
отдельным Node-скриптом на ~30 формулировках до и после фикса.

`askAi()` (резервная бесплатная Cloudflare-модель) теперь тоже получает `siteContext`
(`currentStatus`, `diagnostics.summary`), а не только `inventory` — раньше эти данные уходили
только в OpenAI-путь. Это не решает проблему качества бесплатной модели полностью, но даёт ей
хотя бы реальные факты о сайте для вопросов, не попавших ни в один локальный паттерн.

**Баг с дёрганой анимацией открытия виджета** — найден не эмпирически (эта тестовая среда не
рендерит CSS-переходы и не всегда прогоняет `requestAnimationFrame` для фонового таба — оба
факта подтверждены отдельными пробами), а через анализ самой кривой: `cubic-bezier(.34,1.4,.64,1)`
имеет контрольную точку `y=1.4` — математически это гарантированный овершут (пружина), а
`opacity` завершался за 0.22s, тогда как `transform` ещё «пружинил» до 0.32s — то есть контент
становился полностью непрозрачным, пока ещё продолжал видимо скакать в размере. Заменено на
`cubic-bezier(.22,1,.36,1)` (плавное затухание без овершута) с одинаковой длительностью 0.26s
для обоих свойств; стартовый `scale(.3)` (сильный скачок) смягчён до `scale(.92)`.

**Баг с восстановлением позиции скролла при неродственных ре-рендерах** — код (`wasNearBottom`/
`grew`/`prevScrollTop`, добавленный ещё в коммите `3d8ba15`) оказался логически верным, но
опирался на двойной `requestAnimationFrame`, который в этой тестовой среде не выполняется вовсе
(подтверждено: `console.debug` внутри callback-а ни разу не сработал за несколько прогонов).
Заменено на синхронное присвоение `scrollTop` сразу после `innerHTML=...` — чтение
`scrollHeight` уже само по себе форсирует нужный layout, поэтому двойной rAF был избыточной
подстраховкой. Проверено вживую: ре-рендер без нового сообщения сохраняет позицию скролла
(50px как было), ре-рендер с новым сообщением уводит к низу — оба случая численно подтверждены.

**Надпись в шапке виджета** — оказалась не отдельным «тупым» текстом, а склейкой: серверный
`state.assistant.label` уже содержит «AI-помощник подключён», а клиентский код добавлял к нему
ещё `' на связи'` — получалось «AI-помощник подключён на связи», отсюда и ощущение неуклюжей
фразы. Склейка убрана, используется label как есть (fallback — «Онлайн»).

**Горячие команды в развёрнутом виде чата**: добавлены 2 новые кнопки — «Что ты умеешь?» и
«Позови специалиста поддержки» — видны только при `chatWidgetExpanded`, поверх обычных 4.
По прямому требованию пользователя («если могут сразу срабатывать, как быстрые команды») обе
сделаны через `data-editor-action="quick-*"` (мгновенный вызов `/assistant` и вставка ответа),
а не через `data-prompt-example` (просто вставка текста в поле, требующая ручной отправки) —
это тот самый паттерн, на который пользователь жаловался в прошлом раунде.

**Проверки сайта — не только SEO**: фактически уже была почти дюжина категорий
(`seo`/`content`/`accessibility`/`mobile`/`security`/`performance`/`availability`), просто
клиентский интерфейс их никак не показывал общим списком — отсюда жалоба «не знаю, какие ещё
проверки». Добавлены 3 новые проверки (Open Graph og:title/og:image под новой категорией
`social`, favicon, meta charset) и, главное, на странице «Диагностика» теперь всегда видна
строка из 7 категорий-чипов с количеством найденных замечаний или галочкой при их отсутствии —
проверено вживую («SEO: 2 · Контент ✓ · Доступность: 1 · Мобильная версия ✓ · Безопасность ✓ ·
Скорость ✓ · Соцсети: 1»).

Всё проверено вживую на локальном моке: свободный текст через реальное поле ввода на 5 разных
категорий вопросов подряд (статус/seo/лиды/human/возможности) — конверсация накапливается
корректно, ни разу не повторился шаблонный ответ; после серии сообщений нет горизонтального
скролла, вертикальный скролл работает и корректно стоит внизу. Полный набор тестов: 139/139
(2 теста обновлены — их проверяли на конкретный текст старого ответа/на факт похода в OpenAI,
оба сценария осмысленно изменились в результате этого рефакторинга, не регрессия).

Сознательно не сделано: сам классификатор для вопросов, не попавших ни в один локальный паттерн,
по-прежнему уходит в бесплатную Cloudflare-модель и может путаться — это фундаментальное
ограничение бесплатного пути, снять его может либо оплата OpenAI, либо дальнейшее расширение
локальных паттернов по мере поступления новых жалоб. Общая визуальная модернизация интерфейса
(«выглядит как в 2010 году») по-прежнему не начата — не запрашивалась в этом раунде.

## Три платных функции + доводка чата (2026-08-17)

Клиент прямо сказал: текущий платный функционал (SEO-анализ + правка телефона/графика/кнопки)
не ощущается как то, за что стоит платить — «SEO-анализ выполнит любая дешёвая нейросеть, а
замену блоков и так может сделать через Тильду любой дурак». Обсуждали накрутить более умную
платную модель — отклонено: модель улучшает только формулировки ответа, а не создаёт то, что
нельзя скопировать за вечер. Договорились вместо этого о трёх функциях, которые опираются на
данные, которые уже собирает SiteCare, и которых нет ни у дешёвых SEO-чекеров, ни у самой Tilda.

Одновременно клиент прислал скриншоты с конкретными багами виджета (пустой горизонтальный
скролл внизу чата, ответы одним сплошным абзацем вместо списка) — их сделали первым делом и
задеплоили отдельным раундом, не дожидаясь трёх больших фич.

### Доводка чата
- **Пустой горизонтальный скролл** — та же CSS-ловушка, что чинили раньше на `.assistant-chat`:
  `.chat-suggestions` задавал только `overflow-x:auto` без `overflow-y`, браузер сам
  доопределял вторую ось в `auto`. Добавили `overflow-y:hidden`. Это вскрыло реальный баг под
  скрытым скроллом: ни `.chat-suggestions`, ни `.chat-composer` не имели `flex-shrink:0`, и при
  выросшем (из-за нового списочного ответа) сообщении их могло сжать ниже высоты содержимого —
  кнопки подсказок обрезались. Добавили `flex-shrink:0` обоим, проверено вживую: `clientHeight`
  контейнера кнопок теперь равен `scrollHeight`, кнопки полной высоты (31px).
- **Ответы списком с «продающими» формулировками** — `capabilityAnswer`/`siteStatusAnswer`/
  `diagnosticsAnswer`/`leadsAnswer` в `platform-assistant.js` переписаны с слитных предложений
  через запятую/точку-с-запятой на список по строкам (`• `). Технически это потребовало
  разобраться в двухслойном экранировании: клиентский скрипт целиком лежит внутри серверной
  строки в `platform-ui.js`, поэтому `\n`, написанный напрямую в исходнике этой строки,
  обрабатывается парсером Node ещё на сервере и превращается в реальный перенос строки внутри
  regex-литерала клиентского кода — синтаксическая ошибка «Invalid regular expression: missing
  /» в браузере. Правильный вариант — `\\n` в исходнике (уже был такой в `messageText()`,
  сначала по ошибке «исправил» на `\n`, тесты (`central dashboard contains syntactically valid
  browser JavaScript`) сразу поймали и вернул обратно). Сообщения от AI-классификатора строятся
  как обычные JS-строки в отдельном серверном модуле (`platform-assistant.js`), поэтому там `\n`
  — это просто обычный перенос строки, без этой ловушки; сообщение уходит клиенту через
  JSON (который сам всё правильно экранирует), а не встраивается в код напрямую.
- Заодно нашли и починили баг: `capabilityAnswer()` жёстко возвращал 4 стандартные кнопки в
  поле `suggestions`, из-за чего после вопроса «что ты умеешь» переставали появляться 2
  дополнительные кнопки развёрнутого режима («Позови специалиста поддержки» и сам вопрос «Что
  ты умеешь?»). Теперь `suggestions` не задаётся явно, и включается стандартная логика
  клиента (4 в свёрнутом виде / 6 в развёрнутом).

### Функция 1 — Журнал изменений сайта
Детектирует правки, сделанные прямо в Tilda, а не через SiteCare, сравнивая ежедневные сканы
между собой. Технически самое сложное место — по чему сравнивать: существующие идентификаторы
кандидатов (`candidateId` у кнопок, `originalDigits` у телефонов) включают само содержимое в
идентификатор, поэтому при реальном изменении текста/номера «старое» и «новое» выглядят как два
независимых объекта, а не одно изменение. Решение — `slotKey = blockId|matchIndex`
(ID Tilda-блока + порядковый номер на странице), не зависящий от содержимого. Отслеживаются 7
полей: заголовок, description, H1, график, телефон, текст и ссылка кнопки. Новая ежедневная
джоба `runDueContentAudits` (по образцу уже существующей `runDueHealthScans`), новые таблицы
`platform_content_snapshots` (последнее известное значение) и `platform_content_changes`
(журнал, максимум 200 записей на сайт). Новый эндпоинт `GET .../content-changes`, новая карточка
на странице «Диагностика».

### Функция 2 — Юридическая проверка (152-ФЗ)
Три новые эвристические проверки в `diagnosePage()`: ссылка на политику конфиденциальности,
согласие на обработку персональных данных рядом с формой, баннер cookie. Честно предупреждаем в
интерфейсе: «автоматическая проверка HTML — не заменяет юридический аудит», поскольку баннер,
подключённый сторонним скриптом, в статичном HTML не виден. Отдельно решили важный нюанс:
ссылка на политику обычно живёт один раз в подвале сайта, а не на каждой странице — если судить
по каждой странице отдельно, получится по одному одинаковому замечанию на каждую страницу сайта.
Агрегируется на уровне всего сайта (по аналогии с уже существующим `duplicateFacts()` для
дублей title/description) — одно замечание, если ссылки нет **нигде**, а не N замечаний.
Отдельная карточка-чеклист на странице «Диагностика», плюс новая категория `legal` в общей
строке чипов категорий.

### Функция 3 — Домен/SSL и SLA по доступности
SSL сертификат — сознательно не делали: `fetch()` в Workers не отдаёт метаданные сертификата,
без костыля никак. Домен — через RDAP (`rdap.org`, бесплатно, без API-ключа, сам находит нужный
реестр по домену), новая еженедельная джоба `runDueDomainChecks`, новые поля на `platform_sites`
(`domain_expires_at` и т.д.). Telegram-уведомление за 30 дней до истечения — через уже
существующий `sendNotification()`, без отдельной таблицы «уже уведомляли»: `eventId` строится
как `site_id:domain-expiring:дата`, и `sendNotification` сам не пришлёт дубликат по одному и тому
же `eventId`.

Заодно нашли и попутно починили реальный баг, не связанный с этой задачей напрямую, но
блокирующий тот же `sendNotification()`, которым планировали воспользоваться: у таблицы
`gateway_deliveries` жёсткий `CHECK` на `event_type`, разрешающий только 6 старых значений,
но `sendDigest()` уже давно (с момента появления дайджестов) вызывает
`sendNotification(..., "digest", ...)` — то есть **еженедельный дайджест в Telegram все это время
падал молча** на каждой отправке (сам INSERT — вне try/catch, который ловит только сбои
Telegram). Ни один тест этот путь не проверял. Починили через пересоздание таблицы (в SQLite
нет `ALTER ... ALTER COLUMN` для CHECK) с расширенным списком: добавили `digest` и
`domain-expiring`.

Для аптайма — тоже нашли реальный, тихий баг: `platform_monitor_runs` хранит только последние
1000 строк на сайт, а при опросе раз в 5 минут это ~3.5 дня. `siteReport(env, siteId, days=30)`
при этом молча недосчитывал всё, что старше ~3.5 дней, хотя запрашивали до 90 дней. Добавили
ежедневный рулап в новую таблицу `platform_monitor_daily` (без ограничения по сроку хранения,
джоба `runDueMonitorRollups`) и переписали `siteReport()`: берёт рулап за весь период + сырые
данные только за сегодня (ещё не попавшие в рулап) — числа теперь точные на любом окне. Новая
карточка «Отчёт за месяц» первой на странице «Диагностика» — прямо то, что было нужно клиенту
(«чтобы клиент понимал, за что он заплатил»): доступность в %, средняя скорость ответа,
количество инцидентов, обратный отсчёт до истечения домена.
